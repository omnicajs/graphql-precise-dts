# Как писать тесты

[English](../en/TESTING.md) | [Все языки](../README.md)

## Основное правило: только public API

Поведение проекта тестируется только через публичные точки входа. Тест должен
подавать поддерживаемый внешний вход или реально возможный некорректный вход и
проверять наблюдаемый результат. Нельзя напрямую вызывать внутреннюю функцию,
конструировать промежуточную модель или подменять внутренний модуль, чтобы
попасть в нужную строку отчёта покрытия.

Это правило доказывает достижимость: если сценарий проходит через публичный вход
и выполняет ветвь, у ветви есть путь из реального использования генератора.
Прямой вызов `compileSelectionSet`, `createPlan` или `renderDocument` доказывает
только работу функции с вручную переданными аргументами. Он не доказывает, что
генератор способен построить такие аргументы.

Экспорт функции из внутреннего файла не делает её public API. Границу определяют
экспорты пакета и CLI, а не доступность пути для TypeScript. Наличие существующего
теста внутренней функции не является основанием повторять этот подход.

## Выбор публичного входа

| Проверяемый контракт | Вход теста | Наблюдаемый результат |
|---|---|---|
| Генерация, схемы, documents, paths, cache, публикация | `generateDeclarations` из корня пакета | `outputs`, `diagnostics`, содержимое и состояние файлов |
| Проверка актуальности без записи | `checkDeclarations` | `differences`, диагностика, отсутствие изменений на диске |
| Конфигурация, список проектов, DSL scalar mappings | Соответствующие экспорты корня пакета | Публичное значение, тип или ошибка |
| Команды и загрузка config | Запуск CLI отдельным процессом | Exit code, stdout/stderr, файлы |
| Интеграция Codegen | Plugin из `./codegen`; для интеграции среды — реальный Codegen | Aggregate, диагностика, поведение внешнего инструмента |
| ESM/CJS, package exports, workers | Собранные точки входа пакета | Успешное использование реальным потребителем |

В репозиторных тестах импорт `@/index` допустим как исходная точка входа корня
пакета. Для адаптера допустим исходный entrypoint
`@/integrations/codegen`, соответствующий `./codegen` в сборке.
Это не разрешает импортировать другие файлы из `src/`.

CLI проверяется как команда, а не прямым вызовом `runCli` с искусственной средой.
Настоящие worker-процессы проверяются через API собранного пакета с
`execution.mode: parallel`, без прямого запуска внутреннего обработчика.

Public API не означает, что каждый тест обязан генерировать весь проект:
публичный конструктор `TsType` можно проверить отдельно, если предмет теста — его
контракт. Для правил GraphQL-компиляции входом остаются SDL, документы и конфигурация.

## Порядок написания сценария

1. Сформулируй наблюдаемое правило. Например: «aliases корневых и вложенных полей
   становятся именами свойств ответа».
2. Выбери публичную точку входа, через которую пользователь встречает это поведение.
3. Подготовь минимальную валидную схему, документ и конфигурацию. Для негативного
   сценария нарушь именно проверяемое ограничение; остальные входы должны быть
   корректными, чтобы выполнение не остановилось раньше.
4. Для исправления дефекта сначала получи воспроизводимый красный тест на текущем
   поведении. Ошибка должна относиться к контракту, а не к сломанной подготовке.
5. Проверь результат, его существенные отсутствующие части и побочные эффекты.
6. При изменении генерируемых типов добавь реального TypeScript-потребителя с
   допустимыми и недопустимыми значениями.
7. После исправления проверь соседние состояния и композиции, затем покрытие.

Имя теста описывает обещание пользователю: «сохраняет опубликованное дерево при
ошибке документа», а не «заходит в catch» или «покрывает третью ветку».

## Пример: aliases через генерацию

Сценарий использует временный каталог и публичный API. Проверяются имена свойств
в возвращённой декларации и соответствие опубликованного файла результату.

```ts
import { expect, test } from 'vitest'
import { mkdtempSync, readFileSync, rmSync, writeFileSync } from 'node:fs'
import { tmpdir } from 'node:os'
import { join, resolve } from 'node:path'
import { defineConfig, generateDeclarations } from '@/index'

test('uses aliases for root and nested response properties', async () => {
    const root = mkdtempSync(join(tmpdir(), 'graphql-aliases-'))

    try {
        writeFileSync(resolve(root, 'schema.graphql'), `
            type Query { user: User! }
            type User { id: ID!, name: String! }
        `)
        writeFileSync(resolve(root, 'user.graphql'), `
            query FetchUser {
                payload: user { userId: id, displayName: name }
            }
        `)
        const result = await generateDeclarations(defineConfig({
            root,
            schemas: {
                main: {
                    file: 'schema.graphql',
                    typesModule: '@fixture/schema',
                },
            },
            projects: {
                app: {
                    root: '.',
                    targets: {
                        main: {
                            schema: 'main',
                            documents: { files: ['user.graphql'] },
                            outputs: { tree: { root: 'generated' } },
                        },
                    },
                },
            },
        }))

        expect(result.diagnostics).toEqual([])
        expect(result.outputs).toHaveLength(1)
        const output = result.outputs[0]!
        expect(output.content).toContain('payload: {')
        expect(output.content).toContain('userId: string;')
        expect(output.content).toContain('displayName: string;')
        expect(output.content).not.toMatch(/\b(user|id|name)\??:/)
        expect(readFileSync(resolve(root, output.file), 'utf8')).toBe(output.content)
    } finally {
        rmSync(root, { recursive: true, force: true })
    }
})
```

Для проверки assignability этих деклараций добавь TypeScript-потребителя:
корректная форма с `payload` должна приниматься, форма только с `user` —
отклоняться. Проверка строки показывает написание свойства, но не доказывает
полный контракт типа.

## Что проверять

### Текст деклараций и TypeScript-контракт

Golden-файл полезен для полного результата: экспортов, imports, имён, nullable,
optional и вложенной формы. Ожидание должно быть прочитано и проверено вручную.
Не обновляй его только потому, что генератор выдал другой текст, и не вычисляй
ожидаемый результат тем же алгоритмом, который тестируешь.

Компиляция generated `.d.ts` подтверждает синтаксис и разрешение типов, но даже
тип `any` может успешно компилироваться. Потребитель должен проверять обе стороны:

- допустимые данные ответа и variables принимаются;
- недопустимые данные отвергаются: пропущенное обязательное поле, неправильный
  nullable/list-уровень, неверный alias, несовместимый конкретный тип;
- narrowing по `__typename` предоставляет поля только соответствующего варианта.

Для отрицательных примеров используй точечный `@ts-expect-error` и не подавляй
ошибки потребителя широкими casts, `any` или настройками, скрывающими ошибки
сгенерированных деклараций. Проверяй, что consumer-файл действительно включён
в компиляцию. Одна проверка присутствия строки или отсутствие исключения этого
не заменяет.

### Ошибки и файловые последствия

Проверяй код, severity, источник и позицию диагностики, если они относятся к
контракту сценария. Для ошибок входа, которые отклоняют API-вызов, проверяй
отклонение вызова. Различай предупреждение с успешной публикацией и ошибку,
которая публикацию блокирует.

Сценарий публикации должен проверять фактические файлы. Например: успешный
`generate`, изменение документа на ошибочный, повторный `generate`, затем
равенство дерева последней успешной публикации. Наличие `outputs` в результате
не доказывает запись на диск. При проверке отказа учитывай, что кеш и locks
имеют отдельный жизненный цикл.

Для `check` проверяй differences и отсутствие записи, включая кеш и manifests.
Для повторной генерации проверяй детерминированность текста, manifests и сохранение
timestamps неизменённых файлов, когда это предмет сценария.

### Подготовка данных и отказов

Используй отдельный временный каталог на изолированный сценарий или независимую
группу. Удаляй его в `finally` либо test cleanup. Фикстуры копируй перед генерацией:
тест не должен менять исходные ожидания, зависеть от порядка других тестов или
оставлять файлы в checkout.

Можно создавать входные файлы, изменять ранее опубликованный файл или повреждать
реально созданный кеш, затем снова вызывать public API. Это реальные внешние
состояния. Не создавай вручную `SchemaSnapshot`, `CompiledDocument` или
`PlannedDocument` и не передавай их внутреннему исполнителю.

Не подменяй compiler, planner, renderer, внутренние индексы или результаты их
вызовов. Для системного сбоя предпочитай воспроизводимое состояние файловой
системы или отдельный процесс. Контролируемая подмена внешней системной операции
допустима только для реального отказа этой границы: вход остаётся публичным,
внутренний путь выполняется полностью, а ограничение такого сценария явно
указано. Mock не должен создавать состояние, запрещённое устройством генератора.

## 100% покрытия — обязательный минимум

Для принимаемого изменения требуется **100% statements, branches, functions и
lines** в измеряемом исполняемом коде актуального генератора.
[vitest.config.ts](../../vitest.config.ts) определяет измерение и пороги; они
должны охватывать весь исполняемый код генератора в `src/**`. Команда
`yarn test:coverage` строит отчёт покрытия. Нельзя выдавать покрытие отдельной
подсистемы за покрытие всего генератора.

Отчёт нужно проверять вместе со списком измеряемых файлов, исходными картами и
исключениями, а не только по строке `All files`. Успешный exit code и визуально
округлённый процент не заменяют проверку непокрытых участков. Порог нельзя снижать
для завершения задачи.

Метрики отвечают на разные вопросы:

| Метрика | Что фиксирует карта покрытия |
|---|---|
| Statements | Какие учитываемые инструкции выполнялись |
| Branches | Какие учитываемые альтернативы ветвления выполнялись |
| Functions | Какие учитываемые функции вызывались |
| Lines | Какие учитываемые строки исполнялись |

При входе только через public API такое покрытие даёт минимальное свидетельство
достижимости учитываемого кода на тестовых данных. Оно **не доказывает**, что
assertions обнаруживают неверный результат, все требования реализованы или все
сочетания входов проверены. Даже отсутствующая в реализации проверка не создаёт
непокрытую строку.

### Покрытие состояний шире покрытия инструкций

Statement coverage говорит «инструкция исполнялась». State coverage задаёт
другой вопрос: «в каких состояниях системы и сочетаниях входов она исполнялась,
и проверено ли поведение в этих состояниях?» В этом руководстве состоянием
считаются значимые для контракта данные и условия выполнения, а не только
положение в исходном коде.

Например, один и тот же код объединения selections может выполняться для:

- двух прямых полей, поля и named fragment, двух вложенных fragments;
- обязательного и условного вхождения в разном порядке;
- object, interface или union с разными concrete types;
- nullable-значения и списков с nullable-элементами;
- одинаковых aliases с совместимыми или конфликтующими аргументами.

Отдельные тесты каждого признака могут выполнить все инструкции и ветви, но
не проверить их взаимодействие: например, условный фрагмент внутри abstract
selection, пересекающийся с безусловным вложенным полем. Branch coverage тоже
не считает все комбинации ветвей, последовательности их прохождения и значения
данных на этих путях.

Карты покрытия позволяют посчитать statement coverage в рамках инструментирования.
Для полного state coverage сначала нужно определить всё пространство достижимых
состояний и знаменатель метрики. Глубина GraphQL-документов, значения, графы
фрагментов, последовательности файловых изменений и порядок конкурентных событий
делают это пространство практически необозримым, а без заданных ограничений оно
может быть бесконечным. Процент «покрытия всех состояний» из отчёта V8 получить
нельзя.

Поэтому дополнительно веди явную матрицу значимых состояний и переходов. Выбирай
классы эквивалентности, границы и опасные пересечения; не пытайся механически
перемножить все параметры. Для каждой найденной регрессии сохраняй конкретную
комбинацию как публичный сценарий.

| Область | Примеры состояний и переходов |
|---|---|
| Selections | Alias × повторение × условность × fragment × concrete type |
| Inputs | Nullable/list × default × рекурсия × oneOf × направление scalar mapping |
| Фрагменты | Локальный / импортированный / неоднозначный / недоступный поставщик; транзитивные зависимости и циклы |
| Публикация | Нет дерева → generate → повторный generate → изменение входа → check → ошибка генерации |
| Владение | Файл свой / чужой / изменённый / устаревший; общий output root нескольких targets |
| Исполнение | Холодный / тёплый / повреждённый / отключённый кеш; sequential / реальные workers |

Матрица состояний дополняет обязательные 100% покрытия, а не заменяет их.

### Что делать с непокрытой ветвью

1. Найди путь из public API и минимальный внешний сценарий, который до неё
   доходит. Убедись, что проверяется результат, а не только факт вызова.
2. Если вход отвергается раньше, проверь контракт: возможно, ветвь дублирует уже
   установленный инвариант и не должна существовать.
3. Если состояние невозможно по конструкции, убери избыточную ветвь или вырази
   инвариант типами. Не обходи его через cast промежуточной модели в тесте.
4. Если ветвь достижима только в другом режиме, проверь этот режим через его
   публичный вход и обеспечь отдельное измерение или объединение карт покрытия.
5. Если доказательства не хватает, зафиксируй непокрытое поведение как
   незавершённую работу. Сложность тестирования не отменяет требование.

Не добавляй `ignore`, не сужай `include` и не исключай модуль ради зелёного
процента. Исключённый участок отсутствует в знаменателе, а не становится покрытым.
Техническое ограничение измерения нужно описать с точным участком и отдельным
публичным сценарием; пока измерение не подтверждено, нельзя заявлять полное
покрытие этого участка. Защитное исключение нельзя автоматически считать
недостижимым лишь потому, что его неудобно воспроизвести.

## Где размещать сценарии и как запускать проверки

Тесты публичного API расположены в `tests/scenarios/`, фикстуры —
в `tests/fixtures/cases/`, интеграции — в
`tests/integrations/`. Сценарий группируется по наблюдаемому
контракту: generation, configuration, diagnostics, filesystem или execution,
а не по имени внутреннего модуля.

Проверки типов конфигурации используют `*.test-d.ts`. Потребители generated
деклараций компилируются настоящим TypeScript. Проверки собранного пакета,
включая ESM/CJS и worker runtime, находятся в `tests/package*`.

Для изменения поведения или generated output обязательный подтверждающий запуск:

```bash
yarn lint:fix
yarn tests
yarn test:coverage
```

Для проверки публичных типов используй `yarn test:types`; собранные точки входа
проверяет `yarn test:package`. При локальной работе ограничивай запуск Vitest
файлом нужного сценария, сохраняя полный подтверждающий запуск перед передачей.
Полный `yarn tests` включает проверки типов, runtime-сценарии с генерацией
деклараций во временных каталогах и package-проверки. Состав команд определяется [package.json](../../package.json),
а требования к изменению — [AGENTS.md](../../AGENTS.md).

### Границы измерения

Отчёт должен показывать исполнение через заявленную публичную границу. Прямой
вызов `runCli` не заменяет запуск команды, даже если он выполняет те же строки.

В исходном запуске `parallel` может использовать очередь без worker runtime.
Реальные workers проверяются через собранный пакет. Карты покрытия Vitest не
объединяются автоматически с отдельными процессами `tests/package*`; наличие
package smoke не означает численное покрытие worker-кода. В исходниках также
есть `v8 ignore` с пояснениями. Эти исключения необходимо учитывать при оценке
доказательств: 100% в текущем отчёте относится к его измеряемой области.
Исполняемая обёртка `src/cli.ts` также находится вне карты Vitest; её проверяет
`tests/package-entrypoints.mjs`. Фильтр покрытия сохраняет эту границу, но
не доказывает численное покрытие обёртки.

## Проверка готовности теста

Перед передачей изменения проверь:

- вход публичный, данные соответствуют реальному сценарию;
- исправляемая регрессия воспроизводилась, ожидания выведены из контракта;
- assertions различают правильный результат и существенную неправильную форму;
- TypeScript-потребитель проверяет допустимость и недопустимость данных;
- файловые эффекты и отсутствие нежелательных изменений проверены там, где это
  часть контракта;
- достигнуты обязательные 100% в измеряемой области, проверены её состав и исключения;
- опасные сочетания состояний проверены независимо от зелёной карты покрытия.

При отчёте о готовности называй доказанное поведение и остающиеся ограничения
измерения. Сам по себе процент не является доказательством корректности генератора.
